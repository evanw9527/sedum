## 1. 需求概述

在 Sedum Agent 对话页增加会话级运行时选择，使用户可以在 Snow Grass 自研 `AgentRunner` 与框架实现之间切换，并在相同模型、Skill、知识库和问题下对比执行过程、结果、耗时与 Token。

首个框架运行时选择 **OpenAI Agents SDK**，运行时 ID 为 `openai-agents`；现有实现标记为 `native`。

## 2. 范围

**In scope（本次做）**：

- Agent 对话输入区增加“自研 / 框架”运行时选择。
- 运行时选择按会话持久化，历史会话保持原运行时。
- Snow Grass 提供统一 `AgentRuntime` 协议及 `native`、`openai-agents` 两种实现。
- 两种运行时复用现有模型目录、Skill、知识库上下文、工具执行器和 SSE 事件协议。
- 过程轨迹显示实际运行时、模型、Skill 选择来源、工具步骤、耗时和 Token。
- 对同一输入支持人工创建两个独立会话进行 A/B 对照。
- 框架不可用时明确失败，不在同一次 Run 中静默切换到自研运行时。

**Out of scope（本次不做）**：

- 不在一个已产生消息的会话中混用两个运行时。
- 不同时接入 LangGraph 和 AutoGen。
- 不在本期实现多 Agent 团队 UI、Agent 拓扑编辑器或自动 Handoff 配置页面。
- 不展示模型私有思维链，只展示可验证的决策摘要和工具行动。
- 不重写现有 Workflow 编排内核。
- 首期不新增 SQL、`read_file` 等通用工具，先完成两个 Runtime 对现有 Skill/Tool 能力的对齐和 A/B 验证。

## 5. API 接口清单

### 查询 Agent 运行时

- **路径**：`/api/v1/agent-runtimes`
- **方法**：`GET`
- **用途**：前端获取运行时目录和可用状态。
- **关键响应字段**：
  - `id`（string）：`native` / `openai-agents`
  - `name`（string）：展示名称
  - `available`（boolean）：当前环境是否可用
  - `capabilities`（string[]）：如 `tool_loop`、`handoff`、`session`
  - `unavailable_reason`（string|null）：不可用原因
- **数据来源**：本地 Snow Grass Runtime Registry（拟新增）

### 创建 Agent 会话

- **路径**：`/api/v1/sessions`
- **方法**：`POST`
- **用途**：创建绑定运行时的会话。
- **关键请求参数**：
  - `runtime_id`（string，必填/默认 `native`）：运行时 ID
  - 现有 `title`、`model_id`、`skill_id`、`knowledge_enabled` 保持不变
- **关键响应字段**：
  - `runtime_id`（string）：实际绑定的运行时
- **数据来源**：现有接口扩展

### 流式发送消息

- **路径**：`/api/v1/sessions/{session_id}/messages/stream`
- **方法**：`POST`
- **用途**：使用会话绑定的 Runtime 执行消息。
- **约束**：请求不得覆盖 `runtime_id`；后端以会话持久值为准。
- **新增事件字段**：
  - `runtime_id`
  - `runtime_name`
  - `framework_run_id`（若框架提供）
  - `tool_call_count`
  - `max_steps`

## 8. 技术实施方案

### 8.0 核心术语与边界

| 概念 | 定义 | 是否直接执行外部动作 | 示例 |
|------|------|----------------------|------|
| Agent | 结合用户目标、上下文和运行结果，循环决定下一步 | 通过 Tool 间接执行 | 判断先检索日常记录，再按时间汇总 |
| Skill | 面向一类任务的说明、触发语义、处理步骤、输出约束和允许工具集合 | 否；仅编排和约束 Tool | “日常工作总结”：识别日期、检索记录、去重、按时间输出 |
| Tool | 有明确输入输出契约的原子执行能力，由代码实现并受权限控制 | 是 | `search_knowledge`、`get_current_time`、未来的 `read_file` |
| Knowledge Base | 被检索的数据来源，不负责决策或执行 | 否 | 本地输入、DeepSeek 总结、日常工作记录 |

边界规则：

- Skill 通过 `allowed_tool_ids` 声明可使用的 Tool，不直接绕过 Tool Registry 访问文件、数据库或网络。
- Tool 不负责理解完整业务意图，只完成一次受控、可审计的原子操作。
- Agent 可以在一个 Skill 指导下多轮选择 Tool，并根据 Tool 结果决定继续或结束。
- Native 和 OpenAI Agents Runtime 必须消费同一份 Skill 定义并调用同一套 Tool，避免 A/B 对比失真。

### 8.1 架构决策

| 决策 | 选择 | 原因 | 放弃的方案 |
|------|------|------|-----------|
| 首个框架 Runtime | OpenAI Agents SDK | 与现有自研 Agent Loop 对照最直接；原语较少；提供工具循环、Handoff、Guardrail、Session、Trace；官方支持 OpenAI-compatible endpoint + Chat Completions，DeepSeek 接入路径短 | LangGraph：长任务能力更强但与现有 Workflow/状态层重叠较多；AutoGen：团队抽象偏重，官方对 OpenAI-compatible endpoint 标注未充分测试 |
| Runtime 选择粒度 | 会话级 | 保证上下文、工具轨迹、Token 和故障归因一致 | 每消息切换：同一历史混用两个语义和状态系统，难以比较与恢复 |
| Runtime API | 自有抽象层 | 防止前端和业务直接绑定具体框架，未来可增加 LangGraph | 在路由中直接 `if runtime == ...`：扩展和测试成本高 |
| Framework 模型适配 | `AsyncOpenAI(base_url=DeepSeek)` + `OpenAIChatCompletionsModel` | 官方明确支持 OpenAI-compatible 服务；保留现有模型目录和 Key 管理 | LiteLLM：多一层 beta 兼容适配，当前只有 DeepSeek/GLM 时收益不足 |
| Trace | Snow Grass 本地 Run Event 为主 | DeepSeek 环境下不依赖向 OpenAI 上传 Trace；前端协议统一 | 直接依赖框架云 Trace：数据边界和现有 Sedum UI 不一致 |
| 失败策略 | 明确失败，不静默回退 | A/B 对比必须能归因，避免用户以为运行在框架而实际使用 Native | 自动切换 Native：结果不可审计 |

#### 候选框架工程评分（5 分制）

评分基于当前 Snow Grass 约束，不代表框架的绝对优劣。

| 标准 | 权重 | OpenAI Agents SDK | LangGraph | AutoGen |
|------|------|-------------------|-----------|---------|
| 与现有 AgentRunner 对照和接入成本 | 25% | 5.0 | 3.5 | 3.0 |
| DeepSeek / OpenAI-compatible 适配确定性 | 20% | 5.0 | 4.5 | 3.0 |
| 单 Agent 多工具循环 | 20% | 5.0 | 5.0 | 4.5 |
| 持久化、暂停恢复、HITL | 15% | 3.5 | 5.0 | 3.5 |
| Handoff / 多 Agent 演进 | 10% | 4.5 | 4.5 | 5.0 |
| 与现有 Workflow 重叠程度（越少越高） | 10% | 5.0 | 2.5 | 3.5 |
| **加权结果** | 100% | **4.75** | **4.20** | **3.55** |

选择解释：

- **OpenAI Agents SDK** 最适合作为第一条“框架 Runtime”，验证工具循环、Skill 转换、Handoff 和运行轨迹，不迫使现有 Workflow 重构。
- **LangGraph** 是第二阶段候选；当需求明确包含跨进程恢复、长任务检查点、审批后继续、状态回放时，它的优势会超过 Agents SDK。
- **AutoGen** 更适合已经确定需要多个专业 Agent 团队和复杂协作策略的阶段，不适合作为此次单 Agent Runtime A/B 的第一选择。

### 8.6 Skill 脚本与 Tool 层优化方案

#### 当前问题

- `SkillScriptExecutor.tool_for()` 已把包内 Python 脚本包装成模型 Tool `run_skill_script`，但执行路径由 `AgentRunner` 特判，绕过 `ToolRegistry`。
- `AgentRunner` 能读取 `manifest.tools.allowed`，但当前只把这些 Tool 写进系统提示；真正传给模型的 `model_tools` 只有 Skill Script Tool。
- Runner 内存在脚本参数解析、缓存、执行和事件拼装，Native 与框架 Runtime 难以共享。
- `SkillScriptExecutor` 是策略边界而非 OS 沙箱；不能把它当作可安全执行任意模型生成 Python 的环境。

#### 目标结构

```text
SkillManifest.tools.allowed
          ↓
ToolResolver.bind(skill, run_context)
          ↓
统一 BoundTool 列表
   ├── 固定业务 Tool
   └── run_skill_script（动态限定当前 Skill 包内脚本）
          ↓
Native / OpenAI Agents Tool Adapter
          ↓
ToolDispatcher.execute(tool_call, context)
          ↓
权限校验 → 缓存 → 执行 → 审计 → 标准结果
```

#### 分阶段改造

**阶段 A：统一协议，不改变现有能力**

1. 扩展 `ToolDefinition`：增加 JSON Schema、风险级别和结果类型，不再只有 handler。
2. 新增 `ToolInvocationContext`：包含 `skill_id`、`session_id`、`run_id`、Runtime、刷新意图。
3. 新增 `SkillScriptToolAdapter`：负责动态生成 `run_skill_script` 定义；`SkillScriptExecutor` 仅保留低层受控进程执行。
4. 新增 `ToolDispatcher`：统一完成 allowlist 校验、参数校验、缓存、调用和事件生成。
5. 删除 `AgentRunner` 对 `RUN_SKILL_SCRIPT_TOOL` 的专用分支；所有 Tool Call 进入 Dispatcher。
6. 为兼容旧 Skill，有 `scripts/*.py` 时暂时隐式允许 `run_skill_script` 并记录迁移告警；新版本 Skill 必须显式声明。

**阶段 B：双 Runtime 复用**

1. Native Adapter 将统一 Tool Schema 转为现有 `ChatTool`。
2. OpenAI Agents Adapter 将同一 Tool Schema 转为 SDK Function Tool。
3. 两个 Runtime 获取完全相同的 Bound Tool 集合，框架不得直接执行 Python 或绕过 Dispatcher。
4. 统一输出 `tool.started`、`tool.completed`、`tool.failed`，前端不再把所有工具步骤写成“执行 Skill 脚本”。

**阶段 C：脚本契约和隔离增强（后续）**

1. 固定脚本优先演进为有名称、强类型输入输出的业务 Tool。
2. Skill 脚本输入由松散 CLI 字符串逐步升级为 JSON Schema + JSON stdin/stdout 契约。
3. 在独立 Worker/容器中执行脚本，限制网络、文件系统、CPU、内存和运行时间。
4. 在真正的执行隔离完成前，只允许发布并审核过的 Skill 包脚本；不开放模型临时生成任意 Python。

#### 首期完成标准

- 普通 Tool 和 Skill Script Tool 都能真实进入模型工具列表并被执行。
- `AgentRunner` 与 `OpenAIAgentsRuntime` 不包含任何具体工具名判断。
- Skill 只能调用 `allowed` 集合及当前包允许的脚本。
- 所有调用均保存 Runtime、Skill、Tool、参数摘要、耗时、缓存命中和结果状态。
- 现有已发布脚本 Skill 行为保持兼容，并有清晰的迁移告警。

## 9. 验收标准（AC）

### AC1：运行时选择与持久化

- **Given**：用户位于新对话，两个 Runtime 均可用。
- **When**：选择“框架 · OpenAI Agents SDK”并发送首条消息。
- **Then**：创建的会话 `runtime_id=openai-agents`，刷新页面后仍显示该选择。

### AC2：Native 兼容性

- **Given**：数据库中存在升级前创建的会话。
- **When**：迁移并打开该会话。
- **Then**：会话显示为 `native`，历史消息和原有执行行为不变。

### AC3：会话隔离

- **Given**：当前会话已经存在至少一条用户消息。
- **When**：用户从 Native 切换到 OpenAI Agents。
- **Then**：系统创建新会话并保留输入内容，原会话的 `runtime_id` 和历史不变。

### AC4：相同业务能力

- **Given**：同一模型、Skill、知识库状态和问题。
- **When**：分别在两个 Runtime 中执行。
- **Then**：两者均可获得同一授权工具面和知识上下文，且各自轨迹明确标注 Runtime。

### AC5：错误可归因

- **Given**：OpenAI Agents Runtime 执行失败。
- **When**：后端产生失败事件。
- **Then**：页面显示框架运行失败和错误码，不自动用 Native 生成一个伪成功答案。

### AC6：不展示私有思维链

- **Given**：框架产生多个模型和工具步骤。
- **When**：Sedum 渲染执行轨迹。
- **Then**：只显示模型决策阶段标签、工具名、参数摘要、结果摘要和耗时，不展示隐藏推理文本。

### AC7：可比较指标

- **Given**：Native 与 OpenAI Agents 各完成一次 Run。
- **When**：读取运行记录。
- **Then**：可比较 runtime、模型、Skill、耗时、Token、工具调用次数和成功状态。
